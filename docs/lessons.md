## 2026-05-23 ★★★★★ 「BAE（Behavioral Affiliate Engine）」設計憲法を確立

### 発見
アフィリエイトサイトには3つの方向性がある：
1. **下品系**：「絶対おすすめ！No.1！★★★★★」と煽る競合主流
2. **品位優先系**：アフィリエイトを控えめにしすぎて稼げない
3. **BAE 系（発明）**：行動経済学のナッジで「下品さを排除しながら最大化」

「サブスクやめた」は 3 を選んだ。

### 中核ルール（実装規則として明文化済み・docs/AFFILIATE_DESIGN_PRINCIPLES.md）
- **絶対原則A：7:3ルール**（教育コンテンツ 7 / 代替案 3）
- **絶対原則B：解約導線 > アフィリエイト の絶対序列**（ビジュアルで主役を分ける）
- **絶対原則C：両論併記**（必ずデメリットも書く）

### なぜ重要か
ライフオラクル = 心理的搾取からの解放、サブスクやめた = 経済的搾取からの解放、という哲学の延長線上にある。「アフィリエイト稼ぎサイト」と誤認されたら信頼を失う。

## 2026-05-23 ★★★★★ 「答え→否定→否定つぶし」検証サイクルの発明

### 発見
重要な意思決定（特に設計憲法レベル）をする時、以下の4ステップで検証すると「こじらせ」を防げる：

1. 自分の答えを 1-2 行で明確に出す
2. その答えに対する反論を 5-7 個リストアップ
3. それぞれの反論を検証して「つぶせる/つぶせない」を表形式で判定
4. 全部つぶせれば確定、つぶせなければ答えを修正

### なぜ重要か
- 「考えすぎて壮大な計画になる」リスクを毎回検出できる
- 一方で「思いつきで決めて後悔」も防ぐ
- 弁証法（thesis→antithesis→synthesis）と反証主義の実用版

### 永続化
`~/.claude/skills/proposal-stress-test/SKILL.md` として Claude Code skill 化済み。
ユーザーが「こじらせていないか」「断言できるか」と問うた時に自動的に呼び出される。

## 2026-05-23 ★★★★ Layer 戦略：「捨てない、でも今日は触らない」

### 発見
壮大なビジョン（思想プラットフォーム、ライフオラクル × サブスクやめた連合など）が浮かんだ時、
**完全棄却** でも **即実行** でもなく、**判断トリガー付きの保留** にする。

- Layer 2：アンチ・サブスク思想（保留・判断は1ヶ月後の Layer 1 数値）

### なぜ重要か
- 「いつかやる」幻想は実装の足を引っ張る
- でも「廃案」は将来の選択肢を狭める
- 「判断トリガーを明記した予約」が両者の問題を解消する

## 2026-05-23 ★★★★ ASP の用語マッピング（A8 vs もしも）

### 発見
A8 と もしも で「サイト」「メディア」の意味が違う：
- A8：メディアID（アカウント）+ サイト（複数登録可・ライフオラクル/サブスクやめた等）
- もしも：会員アカウント + メディア（複数登録可）

つまり A8 の「サイト」= もしもの「メディア」。混乱しないよう留意。

### 楽天アフィリエイトの仕組み
- 会員ID（ログインID、例：shinta1999）≠ アフィリエイトID（20桁英数字）
- アフィリエイトID は「リンクを生成」で出力されるURL `https://hb.afl.rakuten.co.jp/hgc/{ID}/?pc=...` から抽出
- 俊雄さんの ID：`039b7990.875038c7.0ab5f5c4.4f8cf5a9`
- 楽天はサイト情報登録（規約3条）が必須。これを忘れると正常レポートが取れない

### Amazon アソシエイトの仕組み
- StoreID（例：shinta1999-22）を商品 URL の `?tag=` パラメータに付与
- 俊雄さんの ID：`shinta1999-22`

## 2026-05-23 ★★ 「設計憲法は思想ではなく実装規則として書く」

### 発見
ドキュメントには2つの層がある：
- **思想層**：「なぜそれをやるのか」（読み物）
- **実装規則層**：「どう書くか」（辞書として使える）

長期に運用するなら**実装規則層**として書くべき。
理由：「迷ったら戻る辞書」にならないと、書いた瞬間に死蔵される。

### サブスクやめたでの適用
`docs/AFFILIATE_DESIGN_PRINCIPLES.md` は思想ではなく実装規則として書いた。
具体的：CSSクラス名、HTML構造テンプレート、禁止語リスト、GA4イベント命名規則。

## 2026-05-23 ★★★★ サブスクは複数プラン（料金体系）がある — 単一月額では不正確

### 発見
ほとんどの主要サブスクは複数の料金プランを持つ：
- Netflix：3プラン（広告つき 890円 / スタンダード 1490円 / プレミアム 1980円）
- Amazon Prime：月額 600円 / 年額 5900円 / 学生プラン
- Spotify：個人 / Duo / 家族 / 学生 の4区分
- DAZN：月額 / 年額月払い / 年額一括 の3パターン

これに対し、サイトの旧 PRICING は1サービス1月額だった。
損失可視化ブロックで「年¥17,880」と表示しても、ユーザーが実際に払っている額と一致しない場合が多く、ナッジの精度が下がる。

### 解決策（実装済み）
- `PRICING` は「代表月額」として後方互換で保持
- 新たに `PLANS` を追加（`{ plans: [{name, monthly, yearly?, popular?, note?}], howToCheck: string }`）
- ヘルパー関数：`getDefaultMonthly` `getPlans` `getPlanCheckHint` `formatMonthlyRange`
- ServicePage に「料金プラン一覧」表セクションを追加（多プランサービスのみ）
- 損失可視化を「プラン別の年額試算リスト」に拡張

### なぜ重要か
- 損失回避ナッジの精度が上がる
- SEO（「Netflix プレミアム 月額」等のロングテール検索を拾える）
- 「自分のプラン確認方法」を併記することで、ユーザー自身に行動を起こさせる起点になる
- 後方互換維持で、まだ plans 未登録のサービスもそのまま動く

### 「最も一般的なプラン」の判定基準（運用ルール）
1. 公式が「スタンダード」「人気No.1」等と表記している場合はそれを採用
2. なければ「料金が中央値のプラン」を選ぶ
3. データに `popular: true` を明示する

### 永続化
- 実装：services.js / ServicePage.jsx / ServicePage.module.css（コミット a2f2e22）
- 設計憲法：AFFILIATE_DESIGN_PRINCIPLES.md の「ピーク・エンド」「損失回避」項に整合
- 次回拡張：来週 Top30 まで、1ヶ月後に全件移行を判断

## 2026-05-23 ★★ A8 のサイト追加の手間と回避策

### 発見
A8 で 42 案件提携済みだが、それは「ライフオラクル」サイトでの審査。
「サブスクやめた」サイトで使うには **8案件追加申請** が必要だった（提携審査はサイト単位）。

### 回避策（重要）
A8 は **広告リンク作成画面で「掲載サイト」を切り替えられる**。
再申請しなくても、既存提携を別サイトで掲載することは技術的には可能。
ただし規約違反リスクがあるので、**新サイトで使う案件は別途申請するのが安全**。
